    1 简介

    本文档是 Google Java™ 编程语言源代码编码标准的完整定义。当且仅当一个 Java 源文件遵循本文档中的规则时，它才被称为符合 Google 风格。

    与其他编程风格指南一样，本文档涵盖的问题不仅包括格式方面的美学问题，还包括其他类型的约定或编码标准。然而，本文档主要关注我们普遍遵循的硬性规则，并避免给出那些无法明确强制执行的建议（无论是通过人工还是工具）。

    1.1 术语说明

    在本文档中，除非另有说明：

    1. 术语 class（类）被广义地用于表示普通类、记录类（record class）、枚举类（enum class）、接口或注解类型（@interface）。
    2. （类的）术语 member（成员）被广义地用于表示嵌套类、字段、方法或构造函数；也就是说，除了初始化块之外的类的所有顶级内容。
    3. 术语 comment（注释）始终指实现注释。我们不使用“文档注释”一词，而是使用常用术语“Javadoc”。

    其他的“术语说明”将不时出现在整个文档中。

    1.2 指南说明

    本文档中的示例代码是非规范性的。也就是说，虽然这些示例遵循 Google 风格，但它们可能并非展示代码的唯一合乎风格的方式。示例中做出的可选格式选择不应作为规则强制执行。

    2 源文件基础

    2.1 文件名

    对于包含类的源文件，文件名由区分大小写的顶层类名（有且仅有一个）加上 .java 扩展名组成。

    2.2 文件编码：UTF-8

    源文件以 UTF-8 编码。

    2.3 特殊字符

    2.3.1 空白字符

    除了行终止符序列之外，ASCII 水平空格字符（0x20）是源文件中唯一允许出现在任何位置的空白字符。这意味着：

    1. 在 char 字面量、字符串字面量以及文本块中，所有其他空白字符都必须进行转义。
    2. 制表符不得用于缩进。

    2.3.2 特殊转义序列

    对于任何具有特殊转义序列的字符（\b、\t、\n、\f、\r、\s、\"、\' 和 \\），应使用该转义序列，而不是对应的八进制（例如 \012）或 Unicode（例如 \u000a）转义。

    2.3.3 非 ASCII 字符

    对于其余的非 ASCII 字符，可以使用实际的 Unicode 字符（例如 ∞），也可以使用等价的 Unicode 转义（例如 \u221e）。如何选择仅取决于哪种方式能让代码更易于阅读和理解，但强烈不建议在字符串字面量和注释之外使用 Unicode 转义。

    提示：在使用 Unicode 转义的情况下，甚至有时在使用实际的 Unicode 字符时，附上解释性注释都会非常有帮助。

    示例：

    示例 说明
    String unitAbbrev = "μs"; 最佳：即使没有注释也非常清晰。
    String unitAbbrev = "\u03bcs"; // "μs" 允许，但没有理由这样做。
    String unitAbbrev = "\u03bcs"; // Greek letter mu, "s" 允许，但笨拙且容易出错。
    String unitAbbrev = "\u03bcs"; 糟糕：读者根本不知道这是什么。
    return '\ufeff' + content; // byte order mark 良好：对不可打印字符使用转义，并在必要时添加注释。

    提示：切勿仅仅因为担心某些程序可能无法正确处理非 ASCII 字符而降低代码的可读性。如果发生这种情况，说明那些程序存在问题，它们必须被修复。

    3 源文件结构

    一个普通源文件按顺序包含以下部分：

    1. 许可证或版权信息（如有）
    2. 包声明
    3. 导入
    4. 有且仅有一个顶层类声明

    每个存在的部分之间用有且仅有一个空行分隔。

    package-info.java 文件与此相同，只是没有类声明。

    module-info.java 文件不包含包声明，并将类声明替换为模块声明，但其余部分遵循相同的结构。

    3.1 许可证或版权信息（如有）

    如果文件中需要包含许可证或版权信息，则应当放在这里。

    3.2 包声明

    每个源文件都必须有包声明。不使用紧凑源文件。（此规则显然不适用于 module-info.java 文件，因为它们具有不同的语法，不包含包声明。）

    包声明不折行。列数限制（第 4.4 节，列数限制：100）不适用于包声明。

    3.3 导入

    3.3.1 不使用通配符导入

    不使用静态或其他形式的通配符（“按需”）导入。

    3.3.1.1 不使用模块导入

    不使用模块导入。

    示例：

    import module java.base;

    3.3.2 不折行

    导入不折行。列数限制（第 4.4 节，列数限制：100）不适用于导入。

    3.3.3 顺序与空行

    导入按如下顺序排列：

    1. 所有静态导入归为一组。
    2. 所有非静态导入归为一组。

    如果同时存在静态和非静态导入，则用单个空行将这两组分隔开。导入之间没有其他空行。

    在每个组内，导入的名称按 ASCII 排序顺序出现。（注意：这与导入行按 ASCII 排序顺序排列不同，因为 '.' 排在 ';' 之前。）

    3.3.4 不对类使用静态导入

    不对静态嵌套类使用静态导入。它们应当通过普通导入来导入。

    3.4 类声明

    3.4.1 有且仅有一个顶层类声明

    每个顶层类都位于其独立的源文件中。

    3.4.2 类内容的顺序

    你为类的成员和初始化块所选择的顺序会对易学性产生巨大影响。然而，对此并没有唯一正确的做法；不同的类可能会以不同的方式排列其内容。

    重要的是，每个类都应当使用某种逻辑顺序，当被问及时，其维护者能够解释清楚。例如，新方法不能只是习惯性地添加到类的末尾，因为那样会产生“按添加日期的时间先后”顺序，而这并不是一种逻辑顺序。

    3.4.2.1 重载：永不拆分

    类中同名的方法应当集中出现在同一个连续的组中，中间不得插入其他成员。这同样适用于多个构造器。即使这些方法或构造器之间的修饰符（如 static 或 private）不同，此规则仍然适用。

    3.5 模块声明

    3.5.1 模块指令的顺序与空行

    模块指令按如下顺序排列：

    1. 所有 requires 指令集中在单个块中。
    2. 所有 exports 指令集中在单个块中。
    3. 所有 opens 指令集中在单个块中。
    4. 所有 uses 指令集中在单个块中。
    5. 所有 provides 指令集中在单个块中。

    每个存在的块之间用单个空行分隔。

    4 格式化

    术语说明：类代码块结构是指类、方法、构造函数或 switch 的主体。请注意，根据第 4.8.3.1 节关于数组初始化器的规定，任何数组初始化器都可以选择性地被视为类代码块结构。

    4.1 大括号

    4.1.1 可选大括号的使用

    大括号用于 if、 else、 for、 do 和 while 语句，即使其主体为空或仅包含单条语句。

    其他可选大括号（例如 lambda 表达式中的大括号）仍然是可选的。

    4.1.2 非空代码块：K & R 风格

    对于非空代码块和类代码块结构，大括号遵循 Kernighan 和 Ritchie 风格：

    • 左大括号前不换行，下文详述的情况除外。
    • 左大括号后换行。
    • 右大括号前换行。
    • 仅当右大括号结束一条语句，或结束方法、构造函数或具名类的主体时，右大括号后才换行。 例如，如果右大括号后面跟着 else 或逗号，则右大括号后不换行。

    例外：在这些规则允许出现以分号（;）结尾的单条语句的地方，可以出现语句代码块，且该代码块的左大括号前要换行。引入此类代码块通常是为了限制局部变量的作用域。

    示例：

    return () -> {
  while (condition()) {
    method();
  }
};

return new MyClass() {
  @Override public void method() {
    if (condition()) {
      try {
        something();
      } catch (ProblemException e) {
        recover();
      }
    } else if (otherCondition()) {
      somethingElse();
    } else {
      lastThing();
    }
    {
      int x = foo();
      frob(x);
    }
  }
};

    第 4.8.1 节枚举类中给出了枚举类的一些例外情况。

    4.1.3 空代码块：可以采用简洁写法

    空代码块或类代码块结构可以采用 K & R 风格（如第 4.1.2 节所述）。或者，也可以在左大括号后立即闭合，中间不包含任何字符或换行（{}），除非它是多代码块语句（直接包含多个代码块的语句：if/else 或 try/catch/finally）的一部分。

    示例：

      // This is acceptable
  void doNothing() {}

  // This is equally acceptable
  void doNothingElse() {
  }

      // This is not acceptable: No concise empty blocks in a multi-block statement
  try {
    doSomething();
  } catch (Exception e) {}

    4.2 代码块缩进：+2 个空格

    每当开始一个新的代码块或类代码块结构时，缩进增加两个空格。当代码块结束时，缩进恢复到之前的缩进级别。缩进级别适用于整个代码块中的代码和注释。（参见第 4.1.2 节非空代码块：K & R 风格中的示例。）

    4.3 每行一条语句

    每条语句后都需换行。

    4.4 列数限制：100

    Java 代码的列数限制为 100 个字符。“字符”是指任何 Unicode 码位。除下文指出的情况外，任何超出此限制的行都必须按第 4.5 节折行中的说明进行折行。

    每个 Unicode 码位都计为一个字符，即使其显示宽度更大或更小。例如，如果使用全角字符，你可以选择比本规则严格要求的位置更早地折行。

    例外情况：

    1. 不可能遵守列数限制的行（例如，Javadoc 中的长 URL，或长 JSNI 方法引用）。
    2. package 声明和导入语句（参见第 3.2 节包声明和第 3.3 节导入）。
    3. 文本块的内容。
    4. 注释中可能需要复制并粘贴到 shell 中的命令行。
    5. 极少数情况下需要使用非常长的标识符，这类标识符允许超出列数限制。在这种情况下，周围代码的有效折行方式应与 google-java-format 生成的结果一致。

    4.5 折行

    术语说明：当原本可能占据单行的代码被拆分为多行时，这种操作称为折行。

    并没有全面、确定性的公式可以准确指出在每种情况下应该如何折行。很多时候，同一段代码有多种有效的折行方式。

    注意：虽然折行的典型原因是避免超出列数限制，但即使代码实际上并未超出列数限制，作者也可以自行决定将其折行。

    提示：提取方法或局部变量或许可以在无需折行的情况下解决问题。

    4.5.1 在何处断开

    折行的首要准则是：优先在更高的语法层级处断开。此外：

    1. 如果在非赋值运算符处断开一行，那么断开位置在该符号之前。（请注意，这与 Google 风格在其他语言（如 C++ 和 JavaScript）中的做法不同。）
      • 这也适用于以下“类运算符”符号：
        • 点分隔符（.）
        • 方法引用的两个冒号（::）
        • 类型边界中的与符号（<T extends Foo & Bar>）
        • catch 代码块中的竖线（catch (FooException | BarException e)）。
    2. 如果在赋值运算符处断开一行，断开位置通常在该符号之后，但两种方式都是可以接受的。
      • 这也适用于增强型 for（“foreach”）语句中的冒号。
    3. 方法名、构造函数名或记录类名与其后面的左圆括号（(）保持在同一行。
    4. 逗号（,）与其前面的记号保持在同一行。
    5. 绝不在紧邻 lambda 或 switch 规则中的箭头处断开一行，除非箭头后面的文本由单个不带大括号的表达式组成，此时可以在箭头后立即断开。示例： 
      MyLambda<String, Long, Object> lambda =
    (String label, Long value, Object obj) -> {
      ...
    };

Predicate<String> predicate = str ->
    longExpressionInvolving(str);

switch (x) {
  case ColorPoint(Color color, Point(int x, int y)) ->
      handleColorPoint(color, x, y);
  ...
}

    注意：折行的主要目标是让代码清晰，而不一定是让代码占据最少的行数。

    4.5.2 续行缩进至少 +4 个空格

    折行时，第一行之后的每一行（即每个续行）相对于原始行至少缩进 +4 个空格。

    当存在多个续行时，缩进可以根据需要超过 +4 个空格。通常，当且仅当两个续行以语法上平行的元素开头时，它们才使用相同的缩进级别。

    第 4.6.3 节关于水平对齐的内容阐述了不鼓励使用可变数量的空格来将某些记号与前面的行对齐的做法。

    4.6 空白

    4.6.1 垂直空白（空行）

    在以下情况中，总是会出现一个单独的空行：

    1. 类的连续成员或初始化器之间：字段、构造器、方法、嵌套类、静态初始化器和实例初始化器。
      • 例外：两个连续字段之间的空行（只要它们之间没有其他代码）是可选的。这类空行可根据需要用于创建字段的逻辑分组。
      • 例外：枚举常量之间的空行在第 4.8.1 节中讨论。
    2. 按本文档其他章节的要求（例如第 3 节源文件结构以及第 3.3 节 Import 语句）。

    只要能提高可读性，单个空行也可以出现在任何地方，例如在语句之间使用空行将代码组织为逻辑子小节。在类的第一个成员或初始化器之前，或者最后一个成员或初始化器之后，既不鼓励也不反对使用空行。

    允许出现多个连续空行，但绝不要求（也不鼓励）这样做。

    4.6.2 水平空白

    除了语言或其他风格规则所要求的地方，并且除了字面量、注释和 Javadoc 内部之外，单个 ASCII 空格仅出现在以下位置。

    1. 将任何关键字（如 if、 for 或 catch）与同一行中紧随其后的左圆括号（(）分隔开
    2. 将任何关键字（如 else 或 catch）与同一行中位于其前面的右花括号（}）分隔开
    3. 在任何左花括号（{）之前，但有两个例外：
      • @SomeAnnotation({a, b})（不使用空格）
      • String[][] x = {{"foo"}};（根据下面的第 10 项，{{ 之间不需要空格）
    4. 在任何二元或三元运算符的两侧。这也适用于以下“类运算符”符号：
      • 分隔多个类型边界的与号（&）： <T extends Foo & Bar>
      • 处理多个异常的 catch 代码块中的竖线（|）： catch (FooException | BarException e)
      • 增强型 for（“foreach”）语句中的冒号（:）
      • lambda 表达式中的箭头： (String str) -> str.length()
        或 switch 规则中的箭头： case "FOO" -> bar();
      但不包括
      • 方法引用中的双冒号（::），其写法如 Object::toString
      • 点分隔符（.），其写法如 object.toString()
    5. 在 ,:; 或强制类型转换的右圆括号（)）之后
    6. 在任何内容与开启注释的双斜杠（//）之间。此处允许多个空格。
    7. 在开启注释的双斜杠（//）与注释文本之间。此处允许多个空格。
    8. 在声明中的类型与标识符之间： List<String> list
    9. 数组初始化器的两个花括号内侧紧邻处的空格是可选的
      • new int[] {5, 6} 和 new int[] { 5, 6 } 都是合法的
    10. 在类型注解与 [] 或 ... 之间。

    本规则绝不应解释为要求或禁止在行首或行尾添加额外空格；它只针对行内部的空格。

    4.6.3 水平对齐：绝不要求

    术语说明：水平对齐是指在代码中添加数量不等的额外空格，目的是使某些标记直接出现在前几行某些其他标记的正下方。

    这种做法是允许的，但在 Google 风格中绝不要求这样做。甚至在已经使用了水平对齐的地方，也不要求维持这种对齐。

    下面是一个先不使用对齐、然后使用对齐的示例：

    private int x; // this is fine
private Color color; // this too

private int   x;      // permitted, but future edits
private Color color;  // may leave it unaligned

    提示：对齐有助于提高可读性，但单纯为了保持对齐而对齐会给未来埋下隐患。例如，考虑一个只涉及一行的修改。如果该修改破坏了原有的对齐，重要的是**不要**仅仅为了重新对齐而在邻近行引入额外的更改。在原本不受影响的行上引入格式更改会破坏版本历史记录、拖慢审阅者的速度，并加剧合并冲突。这些实际考量优先于对齐。

    4.7 分组圆括号：推荐使用

    只有当作者和审阅者一致认为去掉可选的分组圆括号后代码绝不会被误解，并且加上它们也不会让代码更易读时，才可以省略它们。假设每位读者都记住了整张 Java 运算符优先级表是不合理的。

    4.8 特定语法结构

    4.8.1 枚举类

    在枚举常量后面的逗号之后，换行是可选的。此外，还允许添加额外的空行（通常只加一行）。下面是一种可行的写法： 

    private enum Answer {
  YES {
    @Override public String toString() {
      return "yes";
    }
  },

  NO,
  MAYBE
}

    如果枚举类没有方法，且其常量也没有文档注释，则可以选择按照数组初始化器的方式进行格式化（请参见第 4.8.3.1 节关于数组初始化器的规定）。

    private enum Suit { CLUBS, HEARTS, SPADES, DIAMONDS }

    由于枚举类本身就是类，因此适用于类的所有其他格式化规则同样适用于枚举类。

    4.8.2 变量声明

    4.8.2.1 每次声明只声明一个变量

    每个变量声明（无论是字段还是局部变量）都只声明一个变量：不使用诸如 int a, b; 这样的声明。

    例外：在 for 循环的头部中，允许声明多个变量。

    4.8.2.2 在需要时声明

    局部变量不应习惯性地声明在其所属代码块或类代码块结构的开头。相反，局部变量应声明在（在合理范围内）靠近其首次使用的位置，以尽量缩小其作用域。局部变量声明通常带有初始化器，或者在声明后立即进行初始化。

    4.8.3 数组

    4.8.3.1 数组初始化器：可以是“类代码块”形式

    任何数组初始化器都可以选择视同“类代码块结构”来进行格式化。例如，以下写法全部有效（并非详尽无遗的列表）：

    new int[] {           new int[] {
  0, 1, 2, 3            0,
}                       1,
                        2,
new int[] {             3,
  0, 1,               }
  2, 3
}                     new int[]
                          {0, 1, 2, 3}
    4.8.3.2 禁止 C 风格的数组声明

    方括号是类型的一部分，而不是变量名的一部分：应写成 String[] args，而非 String args[]。

    4.8.4 Switch 语句与表达式

    出于历史原因，Java 语言针对 switch 有两种截然不同的语法，我们可以称之为旧式（old-style）和新式（new-style）。新式 switch 在 switch 标签后使用箭头（->），而旧式 switch 使用冒号（:）。

    术语说明：在 switch 代码块的花括号内部，要么是一个或多个 switch 规则（新式），要么是一个或多个语句组（旧式）。一条 switch 规则由一个 switch 标签（case ... 或 default）后跟 -> 以及一个表达式、代码块或 throw 组成。一个语句组由一个或多个各自后跟冒号的 switch 标签，以及随后的一条或多条语句组成；对于最后一个语句组，后面也可以跟零条或多条语句。（这些定义与《Java 语言规范》§14.11 一致。）

    4.8.4.1 缩进

    与其他任何代码块一样，switch 代码块的内容缩进 +2 个空格。每个 switch 标签都以这 +2 的缩进开始。

    在新式 switch 中，只要一条 switch 规则在其他方面符合 Google 编码风格，就可以写在同一行上。（它不得超出列数限制，并且如果包含非空代码块，则在 { 之后必须换行。）此处适用第 4.5 节的折行规则，包括续行的 +4 缩进。对于箭头后带有非空代码块的 switch 规则，适用与其他位置的代码块相同的规则：{ 和 } 之间的行相对于 switch 标签所在行再缩进 +2。 

    switch (number) {
  case 0, 1 -> handleZeroOrOne();
  case 2 ->
      handleTwoWithAnExtremelyLongMethodCallThatWouldNotFitOnTheSameLine();
  default -> {
    logger.atInfo().log("Surprising number %s", number);
    handleSurprisingNumber(number);
  }
}

    在旧式 switch 中，每个 switch 标签的冒号后面都跟一个换行。语句组内的语句再缩进 +2。

    4.8.4.2 贯穿（Fall-through）：必须注释说明

    在旧式 switch 代码块内部，每个语句组要么异常终止（通过 break、continue、return 或抛出异常），要么用注释标记，以表明执行将会或可能会继续进入下一个语句组。任何能表达贯穿（fall-through）含义的注释都足够（通常使用 // fall through）。在 switch 代码块的最后一个语句组中不需要这种特殊注释。示例：

    switch (input) {
  case 1:
  case 2:
    prepareOneOrTwo();
  // fall through
  case 3:
    handleOneTwoOrThree();
    break;
  default:
    handleLargeNumber(input);
}

    请注意，case 1: 后面不需要注释，只需在语句组的末尾添加即可。

    新式 switch 中不存在贯穿。

    4.8.4.3 穷尽性与 default 标签的存在

    Java 语言要求 switch 表达式和许多种类的 switch 语句都是穷尽的（exhaustive）。这实际上意味着，被 switch 判断的每一个可能值都会被某个 switch 标签匹配到。如果 switch 带有 default 标签，那么它是穷尽的；此外，例如当被 switch 判断的值是一个枚举，且该枚举的每个值都被某个 switch 标签匹配到时，它也是穷尽的。Google 编码风格要求每一个 switch 都必须是穷尽的，即使语言本身对此并无要求。这可能需要添加一个 default 标签，哪怕其中不包含任何代码。

    4.8.4.4 Switch 表达式

    Switch 表达式必须采用新式 switch：

      return switch (list.size()) {
    case 0 -> "";
    case 1 -> list.getFirst();
    default -> String.join(", ", list);
  };

    4.8.5 注解

    4.8.5.1 类型使用注解

    类型使用注解紧挨在被注解的类型之前。如果一个注解带有元注解 @Target(ElementType.TYPE_USE)，那么它就是一个类型使用注解。示例：

    final @Nullable String name;

public @Nullable Person getPersonByName(String name);
    4.8.5.2 类、包和模块注解

    作用于类、包或模块声明的注解紧跟在文档块之后，并且每个注解独占一行（即每行一个注解）。这些换行不属于折行（第 4.5 节，折行），因此缩进级别不会增加。示例：

    /// This is a class.
@Deprecated
@CheckReturnValue
public final class Frozzler { ... }

    /// This is a package.
@Deprecated
@CheckReturnValue
package com.example.frozzler;

    /// This is a module.
@Deprecated
@SuppressWarnings("CheckReturnValue") // TODO(b/123): Fix existing CRV violations.
module com.example.frozzler { ... }
    4.8.5.3 方法和构造器注解

    作用于方法和构造器声明的注解规则与上一节相同。示例：

    @Deprecated
@Override
public String getNameIfPresent() { ... }

    例外：如果方法或构造器只有单个无参数的注解，则它可以与签名的第一行出现在同一行，例如：

    @Override public int hashCode() { ... }
    4.8.5.4 字段注解

    作用于字段的注解同样紧跟在文档块之后，但在这种情况下，多个注解（可能带有参数）可以列在同一行上；例如：

    @Partial @Mock DataLoader loader;
    4.8.5.5 参数和局部变量注解

    对于参数或局部变量上的注解，没有特定的格式化规则（当然，该注解是类型使用注解的情况除外）。

    4.8.6 注释

    本节介绍实现注释。Javadoc 在第 7 节“Javadoc”中单独介绍。

    任何换行符之前都可以有任意空白以及随后的实现注释。这样的注释会使该行成为非空行。

    4.8.6.1 块注释风格

    块注释与周围代码的缩进级别相同。它们可以采用 /* ... */ 风格或 // ... 风格。对于多行的 /* ... */ 注释，后续各行必须以 * 开头，并与前一行的 * 对齐。

    /*
 * This is          // And so           /* Or you can
 * okay.            // is this.          * even do this. */
 */

    不要将注释封闭在由星号或其他字符绘制的框中。

    提示：编写多行注释时，如果希望自动代码格式化工具在必要时重新折行（按段落风格），请使用 /* ... */ 风格。大多数格式化工具不会对 // ... 风格的注释块重新折行。

    4.8.6.2 TODO 注释

    对于临时的、短期解决方案的，或者足够好但还不完美的代码，请使用 TODO 注释。

    TODO 注释以全大写的单词 TODO 开头，后跟一个冒号和一个指向包含上下文信息的资源的链接（最好是 bug 引用）。优先使用 bug 引用，因为 bug 会被跟踪并且有后续评论。在这段上下文信息之后，接着写一个由连字符 - 引出的解释性字符串。

    这样做的目的是保持一致的 TODO 格式，以便通过搜索了解如何获取更多详细信息。

    // TODO: crbug.com/12345678 - Remove this after the 2047q4 compatibility window expires.

    避免在添加 TODO 时将个人或团队作为上下文引用：

    // TODO: @yourusername - File an issue and use a '*' for repetition.

    如果你的 TODO 是“在未来某个日期做某事”的形式，请确保包含一个非常具体的日期（“在 2005 年 11 月前修复”）或一个非常具体的事件（“当所有客户端都能处理 XML 响应时移除此代码。”）。

    4.8.7 修饰符

    类和成员的修饰符（如果存在）按《Java 语言规范》推荐的顺序出现： 

    public protected private abstract default static final sealed non-sealed
  transient volatile synchronized native strictfp

    requires 模块指令上的修饰符（如果存在）按以下顺序出现：

    transitive static

    4.8.8 数值字面量

    long 类型的整数字面量使用大写字母 L 作为后缀，绝不使用小写字母（以免与数字 1 混淆）。例如，使用 3000000000L 而不是 3000000000l。

    4.8.9 文本块

    文本块开头的 """ 总是位于新的一行。该行既可以遵循与其他语法结构相同的缩进规则，也可以完全不缩进（即从左页边距开始）。结尾的 """ 位于新的一行，且与开头的 """ 保持相同的缩进，并且在同一行后面可以继续跟其他代码。文本块中的每一行文本的缩进量至少要与开头和结尾的 """ 相同。（如果某一行缩进得更多，那么由该文本块定义的字符串字面量在该行的开头就会包含空格。）

    文本块的内容可以超出列数限制。

    5 命名

    5.1 所有标识符的通用规则

    标识符仅使用 ASCII 字母和数字，并且在下文提到的少数情况下可使用下划线。因此，每个有效的标识符名称都能匹配正则表达式 \w+。

    在 Google 风格中，不使用特殊的前缀或后缀。例如，以下名称不符合 Google 风格：name_、mName、 s_name 和 kName。

    5.2 各类标识符的规则

    5.2.1 包名和模块名

    包名和模块名仅使用小写字母和数字（不使用下划线）。连续的单词直接拼接在一起。例如，com.example.deepspace，而不是 com.example.deepSpace 或 com.example.deep_space。

    5.2.2 类名

    类名以 UpperCamelCase 形式编写。

    类名通常是名词或名词短语。例如， Character 或 ImmutableList。接口名称也可以是名词或名词短语（例如，List），但有时也可以是形容词或形容词短语（例如， Readable）。

    对于注解类型的命名，没有特定的规则，甚至也没有公认的惯例。

    测试类的名称以 Test 结尾，例如 HashIntegrationTest。 如果它覆盖单个类，则其名称为该类的名称加上 Test，例如 HashImplTest。

    5.2.3 方法名

    方法名以 lowerCamelCase 形式编写。

    方法名通常是动词或动词短语。例如， sendMessage 或 stop。

    JUnit 测试方法名中可以出现下划线，用于分隔名称的逻辑组成部分，其中每个部分都以 lowerCamelCase 形式编写，例如 transferMoney_deductsFromSource。测试方法的命名没有唯一正确的方式。

    5.2.4 常量名

    常量名使用 UPPER_SNAKE_CASE：全部使用大写字母，每个单词与下一个单词之间用单个下划线分隔。但究竟什么是常量？

    常量是 static final 字段，其内容是深度不可变的，并且其方法没有可检测到的副作用。这包括基本类型、字符串、不可变值类，以及任何被设为 null 的内容。如果实例的任何可观察状态可能发生改变，那它就不是常量。仅仅打算永不改变该对象是不够的。例如：

    // Constants
static final int NUMBER = 5;
static final ImmutableList<String> NAMES = ImmutableList.of("Ed", "Ann");
static final Map<String, Integer> AGES = ImmutableMap.of("Ed", 35, "Ann", 32);
static final Joiner COMMA_JOINER = Joiner.on(','); // because Joiner is immutable
static final SomeMutableType[] EMPTY_ARRAY = {};

// Not constants
static String nonFinal = "non-final";
final String nonStatic = "non-static";
static final Set<String> mutableCollection = new HashSet<String>();
static final ImmutableSet<SomeMutableType> mutableElements = ImmutableSet.of(mutable);
static final ImmutableMap<String, SomeMutableType> mutableValues =
    ImmutableMap.of("Ed", mutableInstance, "Ann", mutableInstance2);
static final Logger logger = Logger.getLogger(MyClass.getName());
static final String[] nonEmptyArray = {"these", "can", "change"};

    这些名称通常是名词或名词短语。

    5.2.5 非常量字段名

    非常量字段名（无论是静态还是非静态）均以 lowerCamelCase 形式编写。

    这些名称通常是名词或名词短语。例如， computedValues 或 index。

    5.2.6 参数名

    参数名以 lowerCamelCase 形式编写。

    在公共方法中应避免使用单字符参数名。

    5.2.7 局部变量名

    局部变量名以 lowerCamelCase 形式编写。

    即使局部变量是 final 且不可变的，也不将其视为常量，不应按常量的风格命名。

    5.2.8 类型变量名

    每个类型变量均按以下两种风格之一命名：

    • 单个大写字母，后面可选跟单个数字（例如 E、T、 X、T2）
    • 采用类名的形式（参见第 5.2.2 节 类名），后面加上大写字母 T（例如： RequestT、 FooBarT）。

    5.2.9 未命名变量

    凡是在适用的地方，均允许对未命名变量和参数使用 _ 语法。例如：

    Predicate<String> alwaysTrue = _ -> true;

    5.3 驼峰命名法：定义

    有时，将一个英语短语转换为驼峰命名法有不止一种合理的方式，例如当存在首字母缩略词或像 "IPv6" 或 "iOS" 这样不寻常的结构时。为了提高可预测性，Google 风格规定了以下（几乎）确定性的方案。

    从名称的普通文本形式开始：

    1. 将短语转换为纯 ASCII 字符，并移除所有撇号。例如，"Müller's algorithm" 会变成 "Muellers algorithm"。
    2. 将此结果划分为单词，按空格以及任何剩余的标点符号（通常是连字符）进行拆分。
      • 建议：如果任何单词在日常使用中已经具有习惯性的驼峰外观，请将其拆分为组成部分（例如，"AdWords" 变成 "ad words"）。请注意，像 "iOS" 这样的词本身并不是真正的驼峰形式；它不符合任何惯例，因此本建议不适用。
    3. 现在将所有内容（包括首字母缩略词）转为小写，然后仅将以下部分的首字符转为大写：
      • ……每个单词，以生成大驼峰式（upper camel case），或
      • ……除第一个单词外的每个单词，以生成小驼峰式（lower camel case）
    4. 最后，将所有单词连接成一个标识符。请注意，原单词的大小写几乎完全被忽略。

    在极少数情况下（例如多段式版本号），你可能需要使用下划线来分隔相邻的数字，因为数字没有大小写变体。

    示例：

    普通文本形式 正确 错误
    "XML HTTP request" XmlHttpRequest XMLHTTPRequest
    "new customer ID" newCustomerId newCustomerID
    "inner stopwatch" innerStopwatch innerStopWatch
    "supports IPv6 on iOS?" supportsIpv6OnIos supportsIPv6OnIOS
    "YouTube importer" YouTubeImporter
    YoutubeImporter*
    "Turn on 2SV" turnOn2sv turnOn2Sv
    "Guava 33.4.6" guava33_4_6 guava3346

    *可接受，但不推荐。

    注意：在英语中，有些单词是否加连字符是模棱两可的：例如 "nonempty" 和 "non-empty" 都是正确的，因此方法名 checkNonempty 和 checkNonEmpty 也同样都是正确的。

    6 编程实践

    6.1 @Override：始终使用

    只要合法，就必须用 @Override 注解来标记方法。这包括重写超类方法的类方法、实现接口方法的类方法、重新指定超接口方法的接口方法，以及为记录（record）组件显式声明的访问器方法。

    例外：当父方法被标记为 @Deprecated 时，可以省略 @Override。

    6.2 捕获的异常：不忽略

    对捕获的异常不做任何处理，这种做法极少是正确的。（典型的响应方式是记录日志，或者如果认为该异常“不可能发生”，则将其作为 AssertionError 重新抛出。）

    如果确实适合在 catch 块中不采取任何操作，则必须在注释中说明这样做的合理原因。

    try {
  int i = Integer.parseInt(response);
  return handleNumericResponse(i);
} catch (NumberFormatException _) {
  // it's not numeric; that's fine, just continue
}
return handleTextResponse(response);

    6.3 静态成员：使用类进行限定

    当必须限定对静态类成员的引用时，应使用该类的名称进行限定，而不是使用该类类型的引用或表达式。

    Foo aFoo = ...;
Foo.aStaticMethod(); // good
aFoo.aStaticMethod(); // bad
somethingThatYieldsAFoo().aStaticMethod(); // very bad

    6.4 终结方法（Finalizers）：不使用

    不要重写 Object.finalize。终结机制支持计划被移除。

    7 Javadoc

    7.1 格式

    7.1.1 通用形式

    Markdown Javadoc 和传统 Javadoc 均可接受。Markdown Javadoc 如下所示：

    /// Javadoc text is written here,
/// wrapped normally...
public int method(String p1) { ... }

    传统 Javadoc 块的基本格式如下所示：

    /**
 * Multiple lines of Javadoc text are written here,
 * wrapped normally...
 */
public int method(String p1) { ... }

    ……或者如下单行示例所示：

    /** An especially short bit of Javadoc. */

    基本形式总是可接受的。当整个 Javadoc 块（包括注释标记）可以容纳在一行内时，可以改用单行形式。请注意，这仅在没有诸如 @param 之类的块标签时适用。

    7.1.2 段落

    使用传统 Javadoc 时，段落之间以及块标签组（如果存在）之前会出现一个空行——即只包含对齐的前导星号（*）的行。除第一段外，每个段落的第一个词前紧跟 <p>，且其后没有空格。其他块级元素的 HTML 标签（例如 <ul> 或 <table>）之前不加 <p>。

    使用 Markdown Javadoc 时，段落按照 Markdown 的常规方式分隔，即使用除前导 /// 外其余为空白的行。不需要 <p>。

    7.1.3 块标签

    所使用的任何标准“块标签”均按 @param、@return、@throws、@deprecated 的顺序出现，并且这四种类型绝不能出现空描述。当块标签无法容纳在一行内时，对于传统 Javadoc，续行从 @ 的位置缩进四个（或更多）空格；对于 Markdown Javadoc，则精确缩进两个空格。（在 Markdown 中，四个空格的缩进在某些上下文中会被解析为缩进代码块。）

    7.2 摘要片段

    每个 Javadoc 块都以简短的摘要片段开头。这个片段非常重要：它是某些上下文（如类和方法索引）中唯一显示的文本部分。

    这是一个片段——一个名词短语或动词短语，而不是一个完整的句子。它不以 A `Foo` is a... 或 This method returns... 开头，也不构成像 Save the record. 这样完整的祈使句。但是，该片段的大小写和标点符号的使用方式与完整句子相同。

    提示：一个常见的错误是以 /// @return the customer ID 的形式编写简单的 Javadoc。这是不正确的，应当改为 /// Returns the customer ID. 或 /// {@return the customer ID}。

    7.3 何处使用 Javadoc

    至少，必须为每个可见的类、成员或记录组件编写 Javadoc，下文指出的少数例外情况除外。如果顶层类是 public 的，则它是可见的；如果成员是 public 或 protected 的且其所在类是可见的，则该成员是可见的；如果记录组件的所在记录是可见的，则该记录组件是可见的。

    也可以包含额外的 Javadoc 内容，如第 7.3.4 节非必需的 Javadoc 中所述。

    7.3.1 例外：不言自明的成员

    对于“简单、显而易见”的成员和记录组件（例如 getFoo() 方法），如果除了“the foo”之外千真万确没有任何其他值得说明的内容，则 Javadoc 是可选的。

    重要提示：引用此例外作为理由来省略典型读者可能需要了解的相关信息是不恰当的。例如，对于名为 canonicalName 的记录组件，如果典型读者可能根本不知道术语“canonical name”是什么意思，则不要（以注释只会写 @param canonicalName the canonical name 为理由）省略其文档！

    7.3.2 例外：重写

    重写超类型方法的方法上并不总是有 Javadoc。

    7.3.4 非必需的 Javadoc

    其他类、成员和记录组件根据需要或意愿编写 Javadoc。

    每当要用实现注释来定义类或成员的总体目的或行为时，该注释应当改写为 Javadoc（使用 /// 或 /**）。

    非必需的 Javadoc 并不严格要求遵循第 7.1.1、7.1.2、7.1.3 和 7.2 节的格式规则，但当然建议遵循。

    好的风格，让意图更清楚。
